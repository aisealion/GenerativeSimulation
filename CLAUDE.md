# GenerativeSimulation

A common-pool-resource fishery simulation with `agent_count` fishers
(`state/config.json`, default 10) — roster in `state/agents.json`,
(re)generated by `generate_agents.py`. Each fisher harvests by choosing an
effort level, then the whole community proposes and votes on a shared
norm, which the `norm-implementer` agent then implements in code and
commits. The harvest, regrowth, and personality-assignment mechanics
below are ported from Gupta et al.'s CPR-game codebase
(`Codes/Gupta/CPRG_fishing`, branch `origin/hiromu/llm-norm`,
`ostrom3/Agent.py`/`Model.py`) — not this project's own original design.

Each fisher chooses an **effort** level in [0.0, 1.0] rather than a direct
kg amount; actual catch is `effort * stock_kg * HARVEST_PRODUCTIVITY`
(`engine/physics.py:catch_from_effort`, a linear Schaefer-style catch
equation — `HARVEST_PRODUCTIVITY` is the fixed catchability coefficient,
a module constant in `engine/physics.py`, not `state/config.json`). The
lake starts at `CARRYING_CAPACITY_KG` (default 300kg, also its ceiling,
same file) and regrows **logistically** on whatever's left after harvest
(`engine/physics.py:apply_regrowth`):
`stock + GROWTH_RATE * stock * (1 - stock/CARRYING_CAPACITY_KG)` — growth
slows as the stock nears capacity, and unlike a flat per-round add, a
depleted lake regrows very little. There is no rationing when total
demand exceeds the stock (this project's original design had
proportional rationing; Gupta's doesn't) — stock can go negative, which
this project's existing collapse check already treats as a stop
condition.

`generate_agents.py` assigns each agent's personality the same way
Gupta's `CPRModel` does: agent `i` is altruistic iff
`i < agent_count * altruism_ratio` (`state/config.json`, default 0.5) — a
**deterministic index threshold**, not a per-agent random draw — then a
specific norm sentence is picked at random from the matching pool in
`prompts/personality_norms.json` (their two 8-sentence pools, copied
verbatim) to become that agent's `personality_traits`. Re-run it any time
you want to reshuffle the roster or change `agent_count`/`altruism_ratio`
— it also resets `state/runtime.json` to a fresh round 0, since an
existing run's history isn't meaningfully continuable across a roster or
mechanics change.

Run with `python3 -m engine.simulate` (run as a module from the repo root,
not a script path — `engine/` is a package and its internal
`from engine.x import y` imports depend on the repo root being on
`sys.path`, which `-m` gives you and a bare `python3 engine/simulate.py`
doesn't). Two separate model call paths, each with
its own config: the `norm-implementer` still runs as an `opencode` agent
(needs `opencode` configured with a working model — see `opencode.jsonc`,
`litellm/*` for the Otago proxy, `ollama/gpt-oss:120b` for local Ollama);
the fisher agent calls the model directly via `litellm` from
`engine/llm_agents.py` (needs `FISHER_MODEL` set, same `provider/name` convention,
e.g. `litellm/Kimi-K2.5` or `ollama/gpt-oss:120b` — defaults to
`litellm/Kimi-K2.5` if unset — plus `LITELLM_API_KEY` for the `litellm/*`
path). On Aoraki (Otago's HPC), submit
`run_simulation.slurm` instead of running directly. It runs
`apptainer run --nv .../ollama_shellenv.sif "<one command string>"`
directly (matching Otago's own `ollama-batch-example.slurm`), rather than
via the `ollama-env.sh` wrapper — that wrapper doesn't export anything
back to the calling shell, it just execs the same apptainer invocation,
so there's nothing gained by depending on it here. The container's
`OLLAMA_HOST` (a random per-instance port) only exists inside that
container process, so the single command string is
`hpc_ollama_entrypoint.sh`: it writes a job-specific
`.opencode/opencode.json` (gitignored) pointing the `ollama` provider at
the actual `$OLLAMA_HOST`, builds an extended-context variant of each
model to work around Ollama's silent 4096-token default cap, then runs
`engine/simulate.py` from inside that same context — none of this can happen in
the outer SLURM script itself. On Aoraki the two call paths above use two
different local models: `FISHER_MODEL` gets `gpt-oss:20b` (many small,
fast calls per round), `OPENCODE_MODEL` gets `gpt-oss:120b` (one heavier
call per round). Both share the one allocated GPU, so Ollama swaps
between them rather than keeping both loaded — added per-round latency,
not a correctness concern, but worth factoring into `--time`/`MAX_ROUNDS`.
Every round renegotiates:
harvest, then propose + vote + implement, then next round's harvest picks
up whatever the norm-implementer just changed. Resumes from
`state/runtime.json`'s current round, not from round 1 — safe to re-run
after a norm-implementer change. Stops when the lake collapses
(`stock_kg_after_regrowth <= 0`) or after `--max-rounds` (default 100,
override with `python3 -m engine.simulate --max-rounds N`).

Since regrowth is now logistic (see above) rather than a flat add, and
harvest is no longer rationed to the available stock, permanent collapse
is a real, reachable outcome of ordinary play now — not something that
previously required a norm-implementer structural change to trigger.

**CodeGraph on Aoraki — root-caused**: `codegraph sync` was the actual
problem, not `init`. Several earlier theories (restricted network, NFS+
SQLite locking, a daemon/file-watcher issue, non-interactive/no-TTY
invocation, the apptainer container itself) were each individually ruled
out by direct reproduction — `codegraph init .` reliably succeeded in
every standalone test (login node, an actual GPU compute node via `srun`,
interactive and non-interactive `apptainer run`, exact env vars matched),
in low single-digit seconds even under real load. What every one of those
tests had in common, without realizing it: each started from `rm -rf
.codegraph`, so none of them ever actually exercised `sync` — only
`init`. The real job's own `[ -d .codegraph ] → sync` branch was silently
choosing the one path never tested, and a real run's log finally caught
it directly: `"codegraph sync didn't finish within 120s, even running
first, before any Ollama/model work"`. CodeGraph's own docs describe
`sync` as normally triggered *by the file watcher*, not run directly —
plausibly it just isn't designed to be invoked as a one-shot CLI command
the way this script was using it.

Fix: `hpc_ollama_entrypoint.sh` no longer branches on whether
`.codegraph/` already exists — it always `rm -rf .codegraph` then a full
`codegraph init .`, every run, `sync` never called at all. This repo is
19 files; a full rebuild costs low single-digit seconds, so there's no
real cost to never using the incremental path.

## Non-obvious file ownership (not covered by the norm-implementer's own
## repo-shape notes, since these were added after that agent was defined)

- `state/agents.json` — static roster (`name`, `personality_traits`,
  `is_altruistic`) for the fishers, generated by `generate_agents.py`.
  Simulation setup data, not policy — the norm-implementer must never
  write here, only `phases/*.py` reads it.
- `engine/` — the human/Claude-owned orchestrator package (added
  2026-08-25; previously these files sat at repo root). Contains
  `simulate.py`, `llm_agents.py`, `call_log.py`, `phase_base.py`
  (formerly `phases/base.py`), and `memory/` (formerly root-level
  `memory/`) — none of it is on the norm-implementer's allowlist except
  `engine/simulate.py` as a last resort (see below). `mechanisms/`,
  `phases/` (minus `base.py`, now `engine/phase_base.py`), and `prompts/`
  are unaffected by this split — still norm-implementer content, still at
  their original paths. Run as `python3 -m engine.simulate` (a module, not
  a script path) so `engine`'s internal `from engine.x import y` imports
  resolve against the repo root.
- `engine/llm_agents.py` — renders `prompts/persona_template.md` +
  `prompts/role_directives/*.md` + `prompts/phases/*.md` into a prompt and
  calls the fisher model directly via `litellm.completion()` (not through
  opencode) — the system prompt is read from `.opencode/agent/fisher.md`'s
  body, which is no longer invoked as an opencode agent but is kept as the
  single source of that text. Imported by `phases/harvest.py`, `propose.py`,
  `vote.py` as `from engine.llm_agents import call_fisher_agent`. Also
  where `render_notices()` lives (added 2026-08-25) — the generic renderer
  behind `persona_template.md`'s `{notices}` slot; see the fluents note
  below.
- `engine/simulate.py` — the round orchestrator. Schedule-driven, not hardcoded:
  each round it reads `schedule.json`, runs whatever phase is gated on (in
  file order), and dynamically imports `phases.<name>` and calls its
  module-level `PHASE.run(state)` — adding a phase to `phases/` and
  registering it in `schedule.json` is enough to wire it in, no
  `engine/simulate.py` edit needed. Owns writing `state/runtime.json` and
  `state/fluents.json` between phases, and invokes the `norm-implementer`
  opencode agent whenever any phase sets `state["adopted_norm"]`
  (currently only `vote` does). Before committing the norm-implementer's
  changes, `py_compile`s every `.py` file under `mechanisms/`/`phases/` —
  a broken commit there doesn't just fail that round, `reload_project_modules()`
  re-imports from disk every round after too, so it permanently blocks the
  rest of the run until someone manually reverts it (this happened for
  real). On a compile failure, `discard_norm_implementation()` reverts the
  norm-implementer's changes (`git checkout --` + `git clean -fd`, scoped
  to `NORM_IMPLEMENTER_TRACKED_PATHS`) instead of committing them — the
  round continues under the previous mechanics, and the same or a similar
  norm gets another chance to be implemented next time one is adopted.
  **`engine/simulate.py` itself is in `NORM_IMPLEMENTER_TRACKED_PATHS`**
  (was denied to the norm-implementer entirely until 2026-08-20) — the
  compile check above covers it too now, for exactly that reason. This
  followed a real incident worth recording: the norm-implementer edited
  `simulate.py` directly despite `permission.edit: "simulate.py": deny`
  being set at the time — the deny did not actually hold (the edit landed
  on disk; it just never got auto-committed, since `simulate.py` wasn't in
  the tracked-paths list back then, so it sat as an uncommitted change
  until committed by hand). What it "fixed" that way was a bug that
  belonged in `phases/harvest.py` (a missing
  `runtime.setdefault("violations", {})`) — solved in the wrong layer
  purely because it had the opportunity, not because it needed
  orchestrator-level access. `.opencode/agent/norm-implementer.md`'s
  "Editing engine/simulate.py" section instructs it to treat this as a
  last resort, not a shortcut — but that's a prompt-level instruction, not
  a technical guarantee, and the compile-check only catches syntax errors,
  not a semantically broken edit (one that guts the safety-net functions
  themselves, say).

  **Permission model changed 2026-08-25**: the norm-implementer's
  `permission.edit` in `.opencode/agent/norm-implementer.md` switched from
  `"*": allow` plus a denylist to `"*": deny` plus an explicit allowlist
  (`mechanisms/*`, `phases/*`, `prompts/role_directives/*`,
  `prompts/phases/*`, `prompts/phrasing_map.json`, `schedule.json`,
  `state/config.json`, `state/fluents.json`, `engine/simulate.py`) —
  directly motivated by the `deny` reliability gap above: a denylist
  requires every dangerous path to be remembered and listed, and one
  wasn't; a default-deny allowlist doesn't have that failure mode, since
  anything not explicitly named (including every new file added to
  `engine/` by this same restructure) is denied by default rather than by
  enumeration. This doesn't retroactively verify the gap is fixed — the
  underlying `permission.edit` enforcement mechanism itself hasn't been
  re-tested since the incident, so treat "denied" as "denied by this
  config" rather than "guaranteed blocked" until it has been.
- `engine/phase_base.py` (formerly `phases/base.py`) — the `Phase` base
  class every phase module subclasses (`run`, `prompt_fields`,
  `memory_writes`). Human-owned scaffolding, not something a norm round
  edits. Phase files import it as `from engine.phase_base import Phase`.
- `.opencode/agent/fisher.md` — one generic system prompt for both
  fishers (its frontmatter is vestigial; only the body text is read now,
  by `engine/llm_agents.py`, not opencode); personality comes from the
  per-round rendered prompt (`state/agents.json`), not from separate files
  per persona.
- `.opencode/agent/norm-implementer.md` / `.claude/agents/norm-implementer.md`
  — two copies of the same agent definition, kept in sync by hand. The
  opencode copy is the one `engine/simulate.py` actually invokes, and the
  only one whose `permission.edit` allowlist is technically enforced — the
  Claude Code copy's `tools:` frontmatter doesn't support the same
  path-scoped mechanism, but since it's never the one invoked at runtime
  that gap doesn't matter in practice.
- `engine/memory/` (formerly root-level `memory/`) — the Graphiti/Neo4j
  temporal memory layer (`client.py` the shared connection, `write.py`
  episode writes + `IMPORTANCE_BY_EVENT_TYPE`, `query.py` retrieval +
  `PHASE_QUERY_TEMPLATES`). Local-only infra for now (never deployed on
  Aoraki) — `engine/simulate.py`'s `write_memory_episodes()` and
  `engine/llm_agents.py`'s `render_relevant_memories()` both no-op
  gracefully whenever `NEO4J_URI` isn't set or the DB isn't reachable, so
  its absence never blocks a round. Human-owned scaffolding, like
  `engine/llm_agents.py` — the norm-implementer only ever touches it
  indirectly, by adding a `memory_writes()` override to a phase it's
  already editing for another reason.

## Fluent narration and visibility (added 2026-08-25)

`state/fluents.json` records can now optionally carry `narration` (a
plain-language, already in-world-phrased sentence), `visibility`
(`"public"` or `"agent_only"`), and `event_type` (which
`engine/memory/write.py` `IMPORTANCE_BY_EVENT_TYPE` entry it's logged
under) — plus the same three fields prefixed `end_` for the closing side
of the fact (`end_narration`, `end_visibility`, `end_event_type`).
`mechanisms/roles.py` has the primitives: `set_fact()` for any non-role
fact (a sanction, an obligation, a status — `assign_role()` is now a thin
role-shaped wrapper around it), `end_fact()` to close one without
replacing it (accepts its own `narration` for the closing event, not just
the opening one), `visible_facts()` to query what's currently active *or
just-closed-this-round* and visible to a given agent, and
`fact_memory_events()` — pure, no I/O — to turn newly-opened or
newly-closed narrated facts into the same `{event_type, text, agent_id,
group_id}` spec shape `phases/*.py`'s `memory_writes()` already uses.

Two consumers read this, both automatic — no per-mechanism prompt or
memory code required. `engine/llm_agents.py`'s `render_notices()`
concatenates `visible_facts()`'s narration text into `persona_template.md`'s
`{notices}` slot every round for every agent. `engine/simulate.py`'s new
`write_fact_memory_events()` calls `fact_memory_events()` and writes each
spec via `engine.memory.write.write_episode()` — called once per round,
*after* every phase for that round has run (not per-phase like
`write_memory_episodes()`), specifically so a fact set by an early phase
doesn't also look "new" to a later phase's own call and get double-logged.
Gated by `NEO4J_URI` the same as the rest of the memory layer, so its
absence never blocks a round.

This exists because it previously didn't: a fisher banned by
`phases/harvest.py` had no way to learn *why* their catch was zero in any
later round's prompt — the ban lived only in `runtime.json`, and
`render_history()` only ever surfaced `harvested_kg`, never the mechanism's
own `reasoning` field. A record with no `narration` renders nowhere by
design (this is what makes the extension additive — the existing `fisher`
role fluents every agent holds need no migration). Default new
sanction/obligation facts to `visibility="public"` unless a norm
specifically calls for privacy — this project's own adopted norms
consistently specify public ledgers and monitors, so silence shouldn't
default to private. Worth being conscious of, not something fixed here:
defaulting everything public could systematically suppress whatever
private-judgment/reputation dynamics (`visibility="agent_only"`,
`group_id=agent_id` in memory) this architecture is otherwise capable of
surfacing — revisit if that turns out to matter once real data is being
collected from runs.

## Norm-implementer hardening (2026-08-26)

Follow-ups from a review of the 2026-08-25 changes above:

- **`permission.bash` is scoped, not a blanket `allow`.**
  `.opencode/agent/norm-implementer.md`'s `permission.edit` allowlist was a
  real allowlist in name only as long as `bash: allow` sat next to it — an
  unrestricted shell trivially bypasses a file-edit allowlist
  (`echo ... > engine/llm_agents.py`, `sed -i` against any denied path
  accomplish exactly what `edit` blocks, just through a different tool).
  Now scoped the same way as `edit`: `"*": deny`, then explicit `allow`
  patterns for exactly the commands the instructions actually call for
  (`python3 -m py_compile`, `pytest`, read-only `git status`/`diff`/`log`,
  `codegraph`, `grep`). The fallback is `deny`, deliberately not `ask` —
  this agent only ever runs via `opencode run` with nobody present to
  answer a prompt (locally and especially inside the SLURM batch job on
  Aoraki, itself wrapped in a `subprocess.run(..., timeout=3600)`), and
  opencode has a documented open issue where an unanswered `ask` on bash
  hangs rather than failing in headless/server mode. `deny` fails
  immediately, letting the existing compile-check/discard safety net
  handle it the same way it already handles a syntax error.
- **`webfetch`, `websearch`, and `task` (subagent spawning) are explicitly
  denied**, not left unset. An unset permission inherits whatever the
  parent/global opencode config happens to be, which isn't guaranteed to
  be deny — for an agent that's supposed to have a narrow, auditable
  footprint (norm.txt and repo state are its only legitimate inputs),
  explicit beats inherited. (opencode's `tools:` field for disabling a
  tool entirely at the agent level, considered as an alternative, turned
  out to be documented as deprecated/legacy in current opencode
  1.18.14 — `permission` is the only supported mechanism now.)
- **`state/fluents_schema.md`** — new canonical registry of every fluent
  name ever introduced (name + one-line description), added to the
  norm-implementer's allowlist and to `NORM_IMPLEMENTER_TRACKED_PATHS`.
  Exists because CodeGraph can't be relied on to catch a near-duplicate
  fluent name: it indexes code structure (functions, classes, call
  graphs), and a fluent_name is normally just a string literal argument to
  `set_fact()`, not a defined symbol — two separate rounds independently
  inventing e.g. `warning_status` and `caution_flag` for the same concept
  would each look like a clean, unrelated `codegraph_explore` result.
  Step 1 now requires checking this registry before naming a new fluent,
  and updating it in the same round that introduces one.
- **Ambiguous norm parameters route the same as "nothing fits."** A rule
  can match a template's *shape* (`threshold_obligation`, say) while
  leaving the actual threshold value genuinely unrecoverable from
  norm.txt. Decided explicitly (not left implicit): stop and report,
  same as the existing "nothing fits" case — don't pick a conservative
  default and implement it anyway. A wrong-but-implemented guess is
  harder to notice and correct later than a round that visibly didn't
  implement anything, even though it costs a round of forward progress.
- **Step budget exhaustion now has an explicit instruction.** Real
  failures already observed (an empty response at one round, an
  18-character stub — "Reading norm.txt." — with nothing after it at
  others) look exactly like a hard `steps: 500` cutoff mid-tool-call, not
  a principled failure, and nothing previously told the agent what to do
  approaching that limit. Now: stop making tool calls, report whatever's
  done so far in Step 6's existing format, and say explicitly that it ran
  out of budget. Recoverable (the round retries) vs. a silent cutoff,
  which isn't.
- **Step 6's report ends with a fenced `json` block** — `classification`,
  `files_touched`, `regression_pass`, `norm_check_tests_written`,
  `norm_check_tests_pass`, `codegraph_queries`, `ran_out_of_budget` —
  machine-parseable instead of trapped in prose, so a run can be checked
  with `json.loads()` rather than regex-scraping `logs/model_calls.jsonl`'s
  raw response text after the fact.
- **`engine/physics.py`** — `catch_from_effort()` and `apply_regrowth()`
  moved out of `mechanisms/effort.py`/`mechanisms/stock_check.py` (which
  keep only `effort_cap()` and `available_stock()`) into `engine/`, purely
  because it's outside the norm-implementer's `permission.edit` allowlist.
  These two functions are the actual Gupta-ported physics — the catch
  equation and the regrowth rate — not something any norm should be able
  to rewrite; a norm's real levers (caps, deposits, bans, schedules) were
  already implementer-owned and stay that way. `mechanisms/effort.py` and
  `mechanisms/stock_check.py` still exist and are still fully
  implementer-editable — only the two fixed functions left them.
- **`tests/norm_checks/`** — new implementer-writable directory (added to
  the allowlist and to `NORM_IMPLEMENTER_TRACKED_PATHS`) for unit tests
  the norm-implementer writes covering its own mechanism/phase changes,
  required for any structural or `new_phase` round. Distinct from
  `tests/regression/`, which stays a fixed, human-owned suite the
  implementer must never touch — the new suite tests "did this round's
  specific change do what it claims," the old one tests "do the
  invariants that must always hold still hold."
- **New-file creation was already covered, no change needed.** Whether
  `phases/*`-style allowlist globs also permit *creating* a new file
  (`phases/monitoring.py`, say) rather than just editing an existing one
  was worth checking explicitly rather than assuming — confirmed via
  opencode's own docs that `permission.edit` covers write/edit/apply_patch
  uniformly, with no separate rule for new vs. existing paths. The
  existing `phases/*`, `prompts/role_directives/*`, and `prompts/phases/*`
  allows already cover a new phase or a new role's prompt file exactly as
  Step 3's `new_phase`/`role_fluent` guidance already describes.
- **Open question, not resolved here**: whether `"*": deny` +
  specific `allow` overrides in `permission.edit`/`permission.bash`
  actually behaves as documented ("last matching rule wins") on the
  installed opencode version (1.18.14). Two opencode GitHub issues raise
  doubts about exactly this — one reporting `"*": deny` breaking the tool
  entirely rather than letting specific allows through (version 1.1.3,
  much older than what's installed here), another reporting recursive
  `**` glob patterns failing to match (this repo's config only uses
  single-level `*` patterns, not `**`, so may not be affected) — but
  neither is a confirmed match for this exact version and config shape.
  The only way to know for certain is an actual `opencode run` test
  against this agent definition, which hasn't been done. Until it has,
  treat the allowlist as "configured to deny," not "verified to deny" —
  the same caveat already on record for the original `deny`-reliability
  incident this whole allowlist model was built to address.

## Survival economy: consumption, payoff, death (added 2026-08-26)

Comparing our harvest prompt against the actual Gupta et al. paper prompt
turned up a mechanic that had never been ported at all, despite CLAUDE.md
already claiming the harvest/regrowth mechanics were: every villager in
their model owes a fixed `consumption` cost each round against a running
`payoff` balance, and dies the instant that balance goes negative
(`ostrom3/Agent.py::harvest()` / `Model.py::step()` on
`origin/hiromu/llm-norm`). Ours had no equivalent — no cost of living, no
running balance, no death — despite the same paper's prompt text
("Each villager needs to consume {consumption} units of fish daily to
survive. When your payoff becomes negative, you die.") being central to
how a Gupta-model fisher actually reasons about risk.

Ported now, with one deliberate departure: in Gupta's code a single
agent's death halts the *entire* simulation (`if len(agents) !=
len(self.schedule.agents): self.running = False`). Here it just removes
that agent from future rounds and the run continues — chosen specifically
so one early miscalibration doesn't end a whole 100-round run.

- `engine/physics.py` gained `CONSUMPTION_KG = 1.0` (fixed, chosen
  directly rather than derived from Gupta's differently-scaled defaults),
  `apply_consumption(payoff, harvested_kg)`, `is_dead(payoff)`, and
  `alive_agent_ids(agents, runtime)` — the last one is what every phase
  now iterates over instead of the full roster, so death-exclusion can't
  be silently dropped by a future phase rewrite the way a hand-rolled
  per-phase check could be.
- `state/runtime.json` gained `"payoff"` (dict `agent_id -> float`,
  cumulative, never reset) and `"dead_agents"` (list) — both
  simulation-owned, same as everything else in that file.
- `phases/harvest.py` computes the new payoff for every alive agent right
  after computing their kept catch; on death it appends to
  `dead_agents`, opens a `"dead"` fluent (`mechanisms.roles.set_fact()`,
  `visibility="public"`, third-person narration — see the narration-voice
  note added to both norm-implementer specs, prompted by writing this
  narration correctly the first time), and closes their `"fisher"` role
  fluent (`end_fact()`) since a dead fisher no longer holds it. Dead
  agents are omitted from that round's `round_record["agents"]` entirely,
  not zero-placeholder'd — every phase's iteration is consistently
  filtered now, so nothing ever looks one up.
- `prompts/persona_template.md` gained `{survival_status}`
  (`engine/llm_agents.py:render_survival_status()`) — rendered on every
  phase's prompt, not just harvest's, mirroring how Gupta's own prompt
  templates (strategy/punishment/norm-update/vote) all repeat the same
  survival framing rather than stating it once. States the fixed cost and
  the agent's current running balance in plain language; never names
  "payoff," "consumption," or any other code term.
- Closed a gap from the previous "extract fixed physics" pass in the same
  motion: `HARVEST_PRODUCTIVITY`, `GROWTH_RATE`, and `CARRYING_CAPACITY_KG`
  moved out of `state/config.json` (norm-implementer-editable) into
  `engine/physics.py` as module constants, alongside the new
  `CONSUMPTION_KG`. The formulas had already been moved out of the
  norm-implementer's reach two turns earlier, but the *rates* those
  formulas read were still sitting in a file the norm-implementer could
  freely rewrite — a fixed formula reading an editable rate is exactly as
  rewritable as the formula itself. `catch_from_effort()`/`apply_regrowth()`
  dropped their `config` parameter accordingly; `state/config.json` now
  holds only the genuinely implementer-tunable knobs (`agent_count`,
  `altruism_ratio`, `history_window_rounds`, plus whatever
  `effort_caps_kg` a norm adds). `generate_agents.py` (the one other
  reader of the old `carrying_capacity_kg` key, to seed a fresh
  `runtime.json`) now imports `CARRYING_CAPACITY_KG` from
  `engine.physics` directly.

## Prompt layer rules

The `prompts/` tree is the only place agent-facing text lives. It stays
fourth-wall clean: no internal state key names, code identifiers, or the
words "mechanism," "norm," "fluent," "penalty function" ever appear in
rendered prompt text.

- `prompts/persona_template.md` — static skeleton per agent. Slots are
  filled at render time from current state; never edited per-round or
  per-agent. Includes `{notices}` — every currently-active fluent's
  `narration` visible to that agent, rendered generically by
  `engine/llm_agents.py`'s `render_notices()` (see "Fluent narration and
  visibility" above); a norm round never edits this file to add
  per-mechanism notice text, the same way it never edits `{history}`.
- `prompts/role_directives/` — one file per `role_name`, in-world
  phrasing only. The only place role-specific instruction text lives.
- `prompts/phases/` — one instruction template per phase, filled from
  `state/runtime.json` + `state/config.json` at render time.
- `prompts/phrasing_map.json` — maps internal state keys to in-world
  phrases. This is the fourth-wall boundary: internal names and numeric
  mechanics never appear in rendered text directly, only their mapped
  phrasing.
- `prompts/memory_phrasing.py` — same fourth-wall boundary, for the one
  case a static JSON map can't handle: turning a memory record's
  `event_type` into an in-world frame sentence around already-phrased
  text. Every `event_type` in `engine/memory/write.py`'s
  `IMPORTANCE_BY_EVENT_TYPE` needs a case here, or it raises rather than
  leaking unphrased.

### Routing a rule change

- **role_fluent, role_name already has a file in `prompts/role_directives/`**:
  fully parametric — no prompt files touched.
- **role_fluent, role_name is new**: write the config/fluent schema as
  usual, AND add exactly one new file
  `prompts/role_directives/{role_name}.md` with in-world instruction
  phrasing. This is the only prompt edit a role change should ever
  require.
- **new_phase**: same rule — add `prompts/phases/{phase_name}.md`
  alongside the phase's `.py` file.
- **Any other rule**: never touch `prompts/`. If you're tempted to edit
  an individual agent's rendered prompt directly, or hand-write text like
  "this round you are the monitor, your task is X" inline in
  mechanism/phase code, stop — that instruction belongs in
  `prompts/role_directives/monitor.md`, filled generically.

### Validating a prompt-layer change

- Grep any new file under `prompts/` for internal state key names, code
  identifiers, or "mechanism," "norm," "fluent," "penalty function" — any
  hit is a fourth-wall violation and must be rephrased.
- Confirm no diff touches a rendered/output prompt directly — only
  `prompts/persona_template.md`, `prompts/role_directives/*.md`, or
  `prompts/phases/*.md` are legitimate prompt-layer diffs.
